# مرحلهٔ ۶ — کاربران، پروفایل، فرم و مجوز

شاخه: `stage/06-users-permissions`، ادامهٔ مرحلهٔ ۵. وضعیت نصب و شواهد نهایی در انتهای این سند ثبت می‌شود؛ وجود کد به‌تنهایی به معنی نصب موفق نیست.

## دامنهٔ پیاده‌سازی

- شناسهٔ عمومی تصادفی ۱۳کاراکتری با حروف و عدد، بدون مشتق‌کردن از ایمیل یا تلفن؛ شاخص یکتا و مهاجرت حساب‌های قبلی. UUIDهای داخلی و رابطه‌های قدیمی حفظ می‌شوند. قراردادهای جدید `/api/v2` هستند و نشست نسخهٔ ۱ سازگار می‌ماند.
- پروفایل با نام نمایشی، پنج آواتار کارتونی، بارگذاری JPEG/PNG/WebP تا ۲ مگابایت، حذف metadata و تبدیل تصویر در سرور. فایل‌ها فقط در سرویس فایل و volume مستقل نگهداری می‌شوند.
- فرم‌ساز تصویری با ۱۳ نوع فیلد، تب/مرحله، جابه‌جایی، گزینه‌های دوزبانه، الزام، شرط نمایش، نمایش خصوصی/اعضا، پیش‌نویس و انتشار نسخه‌دار. هر کاربر یک فرم منتشرشده دارد؛ به‌صورت پیش‌فرض فرم عمومی و در صورت تخصیص مدیر فرم اختصاصی. پاسخ قبلی هنگام ویرایش/تخصیص در جدول submissions مالک پروفایل حفظ می‌شود.
- همهٔ نشست‌های معتبر پنل مراجع دارند. نقش‌های دیگر افزوده می‌شوند؛ تغییر فضای کاری صرفاً نمایش را عوض می‌کند و جای کنترل مجوز در مالک داده را نمی‌گیرد.
- مدیر کل: دعوت کاربر با ایمیل تعیین رمز، ویرایش پروفایل، تخصیص فرم، اعطا/لغو نقش و غیرفعال‌سازی با ابطال نشست. حذف به‌صورت غیرفعال‌سازی است و سوابق را پاک نمی‌کند. آخرین مدیر کل حذف نمی‌شود؛ برای غیرفعال‌سازی مدیر ابتدا باید نقش او حذف شود.
- سازمان/شعبه و نقش در محدودهٔ مشخص. مدیر سازمان فقط نقش‌های مجاز در همان محدوده را مدیریت می‌کند؛ نقش مدیر کل یا دسترسی سراسری قابل اعطا توسط او نیست. مجوزها بدون cache بررسی می‌شوند تا لغو دسترسی در درخواست بعدی اثر کند.
- رضایت نسخه‌دار در سرویس مستقل consent؛ پس‌گرفتن رضایت نمایش به دیگر اعضا و ثبت درخواست جلسه را متوقف می‌کند. مجوز مدیر برای رسیدگی به اطلاعات خصوصی مستقل است.
- درخواست واقعی جلسه با استاد فعال، بررسی توسط همان استاد و لغو توسط صاحب درخواست. این بخش رزرو قطعی زمان، پرداخت و ظرفیت تقویم نیست؛ آن‌ها متعلق به مرحلهٔ ۹ هستند. ابزارهای تخصصی نقش‌های سایر مراحل و پیام‌رسان کامل همچنان خارج از دامنه‌اند؛ صفحات واقعی دادهٔ نمونهٔ جلسات و پیام‌ها نمایش نمی‌دهند.

## مرز سرویس‌ها

هویت مالک حساب و نشست؛ organization مالک سازمان، عضویت و grant؛ profile مالک فرم و پاسخ؛ file مالک بایت تصویر و ACL آن؛ consent مالک سابقهٔ رضایت؛ booking مالک درخواست جلسه است. ارتباط فقط HTTP داخلی همراه با کلید زیرساخت و توکن نشست است. مالک هر عملیات مستقل مجوز را بررسی می‌کند. هیچ سرویس به دیتابیس سرویس دیگر وصل نمی‌شود. تاریخچهٔ عملیات حساس در تراکنش سرویس مالک ثبت می‌شود؛ تجمیع مرکزی کل سامانه در audit-service هنوز اجرا نشده است.

مسیرهای مرورگر: `/{locale}/account`، `/account/profile`، `/members/{public_id}`، `/admin/users`، `/admin/forms`، `/admin/organizations` و `/admin/audit` با پیشوند نصب `/vianoor`. BFF کوکی HttpOnly را به Bearer داخلی تبدیل می‌کند؛ ورودی‌های تغییردهنده نیازمند Origin معتبر و JSON هستند.

## نصب و آزمون مستقل

```bash
docker build -f infra/Dockerfile -t vianoor-services:stage6 .
docker build -f infra/web.Dockerfile --build-arg NEXT_PUBLIC_BASE_PATH=/vianoor -t vianoor-web:stage6 .
bash scripts/deploy/stage06-test.sh
```

نصب آزمایشی با پروژهٔ Compose مستقل `vianoor-stage6-test` و کلیدها و دیتابیس‌های جدا زیر `.cache/stage06-test` ساخته می‌شود. وب و SMTP آزمایشی فقط روی loopback میزبان قابل دسترسی‌اند. آزمون integration از SMTP واقعی به Mailpit، API واقعی و PostgreSQL مستقل استفاده می‌کند؛ تحویل به ایمیل اینترنتی را ادعا نمی‌کند. fixture مرورگر فقط حساب‌های مصنوعی محیط آزمایشی است و در Git یا تصویر Docker قرار نمی‌گیرد.

پس از آزمون، در checkout تمیز `/opt/vianoor-stage06`:

```bash
bash scripts/deploy/stage06.sh
```

اسکریپت پیش از مهاجرت از PostgreSQL نسخهٔ پشتیبان خصوصی می‌گیرد، کلیدهای مرحلهٔ ۵ را حفظ می‌کند، شبکه/volumeهای نصب جاری را نگه می‌دارد و در شکست فعال‌سازی تصاویر قبلی identity/gateway/web را بازمی‌گرداند. پس از استفادهٔ واقعی از مرحلهٔ ۶، downgrade دستی باید اثر غیرفعال‌سازی کاربران و مجوزها را در نظر بگیرد؛ restore کورکورانهٔ دیتابیس مجاز نیست. فایل‌های `infra/local` و نسخهٔ پشتیبان نباید چاپ یا وارد Git شوند.

مدیر کل اولیه فقط بعد از مشخص‌شدن حساب مالک و تأیید ایمیل آن تعیین می‌شود. روی سرور شناسه را بدون ثبت در history بخوانید:

```bash
read -r -p 'Verified owner public ID: ' owner_id
printf '%s' "$owner_id" | docker exec -i vianoor-stage4-organization-service-1 node scripts/users/bootstrap-admin.mjs
unset owner_id
```

این ابزار فقط وقتی هنوز مدیر کلی وجود ندارد کار می‌کند؛ پس از آن اعطای نقش از مدیریت کاربران انجام می‌شود. هیچ مدیر عمومی، رمز پیش‌فرض یا نقش اعطاشده با ثبت‌نام عادی وجود ندارد.

## شواهد — ۲۰۲۶/۰۹/۲۶

- `npm run check`: موفق؛ معماری، lint، ۳۰ آزمون واحد، ساخت همهٔ سرویس‌ها و دو برنامه، typecheck.
- `npm run smoke`: موفق؛ ۳۲ سرویس در حالت scaffold محلی و مسیرهای فارسی/انگلیسی web/admin. readiness سرویس scaffold عمداً 503 است؛ این نتیجه جای اتصال واقعی را نمی‌گیرد.
- آزمون integration در Compose مستقل سرور: موفق با PostgreSQL، هفت سرویس فعال و SMTP به Mailpit؛ شناسه، ثبت‌نام، رضایت، پاسخ فرم، تصویر، مالکیت، عبور از tenant، آخرین مدیر، درخواست جلسه و ابطال نشست/نقش بررسی شد.
- Playwright دسکتاپ و موبایل: هر دو جریان کامل موفق؛ دعوت و ایمیل تعیین رمز، تکمیل فرم مرحله‌ای، پنج آواتار و آپلود عکس، اعطا/لغو نقش، ساخت/انتشار/تخصیص فرم تب‌دار، پروفایل اعضا و رد API مدیر برای مراجع. تأخیر عمدی پاسخ رضایت نیز آزموده شد.
- انتخاب‌گر و منوی اختصاصی پیش‌نمایش‌ها: آزمون دسکتاپ و موبایل موفق. آزمون نسخه، سیاست کش و جلوگیری از دسترسی بدون نشست به پنل مدیر در محیط نصب آزمایشی نیز موفق.
- خطاهای کشف و اصلاح‌شده: بسته‌شدن مسیر سلامت با middleware داخلی؛ ناسازگاری باینری تصویر با CPU سرور؛ بازنویسی ویرایش زودهنگام فرم جدید؛ ذخیره پیش از دریافت وضعیت رضایت.

## نسخه، منو و تاریخچهٔ Git

نسخهٔ فعلی `V6.0.1` در هدر پنل‌های واقعی و پابرگ صفحات عمومی دیده می‌شود. مسیر `/vianoor/api/version` همان نسخه را با `no-store` برمی‌گرداند؛ HTML صفحات نیز `private, no-cache, no-store` دارد و دارایی‌های دارای نام hash همچنان قابل cache هستند.

اصلاح منوی پیش‌نمایش و دراپ‌داون در `stage/03-responsive-ui` ثبت شد و با merge بدون squash به `stage/05-multimethod-auth` و سپس `stage/06-users-permissions` رسید. انتخاب‌گر پنل واقعی فقط نقش‌ها و scopeهای پاسخ سرویس مجوز را نمایش می‌دهد؛ ثبت‌نام عادی هیچ نقش مدیریتی ایجاد نمی‌کند. بخش‌های تخصصی مراحل آینده در منو معرفی می‌شوند اما داده یا عملیات ساختگی ندارند.

تصاویر آمادهٔ Sharp به SSE4.2 نیاز داشتند و پردازندهٔ مجازی فعلی آن را ارائه نمی‌کند. Dockerfile نسخهٔ مشخص و checksumدار libvips و Sharp را از سورس می‌سازد؛ تبدیل JPEG، جهت EXIF، resize، خروجی WebP و حذف metadata در خود تصویر کانتینر کنترل می‌شود. مرجع: [نصب Sharp](https://sharp.pixelplumbing.com/install/).

مدیر کل اولیه هنوز نیازمند تعیین ایمیل حساب تأییدشدهٔ مالک است. حساب آزمایشی یا مدیر با رمز پیش‌فرض روی سایت اصلی ایجاد نشده است. شاخه‌ها در Git محلی و checkout سرور ثبت شده‌اند؛ push مستقیم به GitHub به علت نبود احراز هویت Git در هر دو محیط انجام نشده است.

## نصب اصلی

نصب `V6.0.1` روی `https://srun.ir/vianoor` پس از پشتیبان‌گیری خصوصی از PostgreSQL انجام شد. هفت سرویس دامنه/درگاه و وب سالم‌اند؛ SMTP آماده و صف pending صفر گزارش شد. کنترل مستقیم پایگاه هویت تعداد شناسه‌های عمومی نامعتبر را صفر نشان داد. تعیین مدیر کل مالک همچنان منتظر مشخص‌شدن حساب توسط کاربر است.

آزمون عمومی روی دامنهٔ اصلی نیز در دسکتاپ و موبایل موفق شد: نسخه، no-store، تغییر محیط مدیر به استاد، منوی اختصاصی و منع ورود بدون نشست به مدیریت کاربران. مشکل لمس زودهنگام منوی موبایل با غیرفعال‌بودن کنترل‌ها تا پایان hydration اصلاح و دوباره روی دامنه آزموده شد. محیط Compose آزمایشی پس از اتمام کار متوقف شد؛ volumeها برای بازتولید آزمون حفظ شدند.
