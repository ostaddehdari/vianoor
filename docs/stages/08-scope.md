برای **مرحله ۸**، محدوده کار را این‌طور دقیق می‌بندیم تا بعداً هنگام پیاده‌سازی معلوم باشد چه چیزهایی باید کامل شوند و چه چیزهایی مربوط به مراحل بعد است.

# مرحله ۸ — اساتید، تخصص‌ها، خدمات و فایل‌ها

هدف این مرحله ساخت کامل **زیرسیستم استاد** است؛ یعنی از لحظه درخواست استادشدن، بررسی مدارک و تأیید صلاحیت، تا انتشار پروفایل، تعریف تخصص‌ها، خدمات و تعرفه‌ها و همچنین زیرساخت امن فایل.

## ۸.۱. ساخت مدل «استاد»

کاربر عادی بتواند درخواست تبدیل‌شدن به استاد را ثبت کند. برای هر استاد اطلاعات حرفه‌ای جدا از حساب کاربری نگهداری می‌شود، از جمله:

- نام نمایشی و عنوان علمی
- تصویر پروفایل حرفه‌ای
- بیوگرافی کوتاه و کامل
- سوابق علمی و اجرایی
- تحصیلات
- حوزه‌های فعالیت
- سال‌های تجربه
- زبان‌های قابل ارائه خدمت
- شهر/کشور در صورت نیاز
- وب‌سایت و شبکه‌های اجتماعی، در صورت مجاز بودن
- وضعیت استاد
- وضعیت نمایش عمومی پروفایل

و وضعیت‌هایی مانند:

`DRAFT → SUBMITTED → UNDER_REVIEW → NEEDS_CHANGES → APPROVED → SUSPENDED → REJECTED`

---

# ۸.۲. تخصص‌ها و حوزه‌های موضوعی

یک ساختار سلسله‌مراتبی برای تخصص‌ها طراحی می‌کنیم.

مثلاً:

**مشاوره دینی**
→ اعتقادی  
→ احکام  
→ خانواده  
→ تربیت فرزند  
→ اخلاق  
→ ازدواج  
→ نوجوان  
→ شبهات

یا:

**روان‌شناسی**
→ خانواده  
→ کودک  
→ نوجوان  
→ ازدواج

ادمین بتواند:

- دسته ایجاد کند
- زیر‌دسته ایجاد کند
- ویرایش کند
- غیرفعال کند
- ترتیب نمایش را تعیین کند
- برای دسته آیکون/تصویر تعیین کند

هر استاد نیز می‌تواند چند تخصص داشته باشد.

اما صرف انتخاب استاد باعث تأیید تخصص نمی‌شود؛ برای هر تخصص می‌توان وضعیت مستقل داشت:

- در انتظار بررسی
- تأیید شده
- رد شده

در نتیجه ممکن است یک استاد در «مشاوره خانواده» تأیید شده باشد ولی درخواست تخصص «حقوق» او هنوز تأیید نشده باشد.

---

# ۸.۳. زبان‌های استاد

یک جدول مرکزی برای زبان‌ها ایجاد می‌شود؛ مثلاً:

- فارسی
- عربی
- انگلیسی
- ترکی
- اردو

برای هر استاد نیز سطح زبان قابل ثبت است:

- زبان مادری
- مسلط
- متوسط
- مکالمه

بعداً این داده برای **جستجوی استاد و رزرو** استفاده خواهد شد.

# ۸.۴. مدارک و مستندات استاد

استاد بتواند مدارک مختلف بارگذاری کند، مانند:

- مدرک تحصیلی
- مدرک حوزوی
- گواهینامه تخصصی
- مجوز حرفه‌ای
- کارت شناسایی
- رزومه
- معرفی‌نامه
- سایر مدارک

برای هر مدرک اطلاعاتی مانند این نگهداری می‌شود:

- نوع مدرک
- عنوان
- مؤسسه صادرکننده
- شماره مدرک
- تاریخ صدور
- تاریخ انقضا
- فایل
- توضیحات
- وضعیت بررسی

و:

`PENDING / APPROVED / REJECTED / EXPIRED`

ادمین می‌تواند روی هر مدرک یادداشت بررسی ثبت کند.

# ۸.۵. فرایند تأیید صلاحیت استاد

یک Workflow واقعی بررسی استاد می‌سازیم.

### جریان اصلی

`ثبت درخواست`

↓

`تکمیل اطلاعات حرفه‌ای`

↓

`انتخاب تخصص`

↓

`بارگذاری مدارک`

↓

`ارسال برای بررسی`

↓

`بررسی مدیر`

↓

یکی از این سه حالت:

`تأیید`

یا

`نیازمند اصلاح`

یا

`رد`

اگر نیازمند اصلاح باشد، استاد دقیقاً می‌بیند چه مواردی باید اصلاح شود و پس از اصلاح دوباره پرونده را ارسال می‌کند.

---

# ۸.۶. پنل بررسی استاد در مدیریت

در داشبورد مدیریت بخش مستقلی با عنوان مثلاً:

**اساتید / درخواست‌های تأیید**

داریم.

ادمین بتواند استادان را براساس:

- وضعیت
- تخصص
- تاریخ درخواست
- مدارک ناقص
- مدارک منقضی
- زبان
- نام
- ایمیل
- شماره تلفن

فیلتر کند.

صفحه بررسی استاد نیز تمام اطلاعات و مدارک را در یک صفحه نشان دهد.

ادمین بتواند:

- کل درخواست را تأیید کند
- رد کند
- درخواست اصلاح بدهد
- یک مدرک را جداگانه رد یا تأیید کند
- یک تخصص را جداگانه تأیید کند
- یادداشت داخلی بگذارد
- دلیل تصمیم را برای استاد ارسال کند.

---

# ۸.۷. نشان تأیید استاد

پس از تأیید صلاحیت، استاد دارای وضعیت Verified می‌شود.

در پروفایل عمومی می‌توان نمایش داد:

**استاد تأییدشده**

ولی اطلاعات خصوصی یا اسناد تأیید هویت عمومی نخواهند شد.

همچنین تأیید می‌تواند دارای تاریخ اعتبار باشد تا در آینده امکان **بازبینی صلاحیت** داشته باشیم.

# ۸.۸. خدمات استاد

هر استاد پس از تأیید بتواند خدمات خودش را تعریف کند.

مثلاً:

هر Service شامل:

- دسته‌بندی

- نیازمند رزرو یا بدون رزرو

خواهد بود.

# ۸.۹. تعرفه خدمات

سیستم تعرفه را طوری طراحی می‌کنیم که بعداً مجبور به تغییر معماری نشویم.

مثلاً یک استاد می‌تواند داشته باشد:

| خدمت | مدت | قیمت |
|---|---:|---:|
| مشاوره متنی | — | ۲۰۰ هزار |
| تماس صوتی | ۳۰ دقیقه | ۳۰۰ هزار |
| تماس تصویری | ۳۰ دقیقه | ۴۰۰ هزار |
| تماس تصویری | ۶۰ دقیقه | ۷۰۰ هزار |

در این مرحله **تعریف تعرفه** انجام می‌شود.

پرداخت، رزرو و تسویه مالی استاد می‌تواند در مراحل بعد به آن متصل شود.

---

# ۸.۱۰. وضعیت انتشار خدمات

هر خدمت وضعیت خواهد داشت:

`DRAFT`

`PENDING_REVIEW`

`PUBLISHED`

`REJECTED`

`DISABLED`

بنابراین می‌توان تعیین کرد که خدمات استاد مستقیماً منتشر شوند یا ابتدا نیاز به تأیید مدیریت داشته باشند.

این رفتار نیز از تنظیمات ادمین قابل کنترل خواهد بود.

# ۸.۱۱. دیدگاه‌ها و موضوعات استاد

بخش دیگری برای محتوای حرفه‌ای استاد ایجاد می‌کنیم تا استاد بتواند برای خودش حوزه‌ها و دیدگاه‌های علمی ثبت کند.

مثلاً:

**موضوع:** تربیت نوجوان

**دیدگاه استاد:**  
متن معرفی رویکرد، تخصص و شیوه مشاوره استاد در این حوزه.

این بخش با «نظر کاربران / Review» متفاوت است.

Review و امتیاز کاربران بهتر است همراه سیستم جلسات و رزرو پیاده شود.

# ۸.۱۴. زیرساخت مرکزی فایل

در این مرحله فایل‌ها را به شکل اصولی از برنامه جدا می‌کنیم.

به‌جای ذخیره مستقیم فایل‌های اصلی داخل سرور برنامه، یک **File Service** مرکزی ایجاد می‌کنیم.

معماری:

`Frontend`

↓  

`API`

↓

`File Service`

↓

`Object Storage`

برای Object Storage می‌توانیم از سرویس S3-compatible استفاده کنیم؛ بنابراین بعداً امکان استفاده از MinIO، AWS S3 یا سرویس‌های مشابه وجود خواهد داشت.

# ۸.۱۵. فایل عمومی و خصوصی

فایل‌ها حداقل دو نوع خواهند داشت.

### Public

مثل:

- آواتار استاد
- تصویر خدمت

### Private

مثل:

- کارت ملی
- مدرک تحصیلی
- گواهینامه
- مدارک احراز هویت

مدارک خصوصی **نباید URL عمومی دائمی داشته باشند**.

کاربر مجاز از API درخواست می‌دهد و سیستم پس از بررسی Permission یک URL موقت یا Signed URL ایجاد می‌کند.

# ۸.۱۶. کنترل دسترسی فایل

برای هر فایل اطلاعات مالک و سطح دسترسی ذخیره می‌شود.

مثلاً:

`OWNER_ONLY`

`ADMIN_ONLY`

`AUTHORIZED_USERS`

`PUBLIC`

بنابراین حتی اگر کسی شناسه فایل را حدس بزند، قادر به دریافت فایل خصوصی نخواهد بود.

---

# ۸.۱۷. کنترل نوع فایل

فقط Extension بررسی نمی‌شود.

مثلاً کاربری نتواند:

`virus.exe`

را به:

`certificate.pdf`

تغییرنام دهد و آپلود کند.

سیستم باید:

- extension
- MIME Type
- File Signature

را بررسی کند.

---

# ۸.۱۸. محدودیت حجم فایل

محدودیت براساس نوع فایل قابل تنظیم است.

مثلاً:

- Avatar: حداکثر 5MB
- تصویر: 10MB
- PDF: 20MB
- مدرک: 20MB
- ویدئو: مقدار قابل تنظیم

این اعداد از تنظیمات مدیریت قابل تغییر خواهند بود و Hard-code نمی‌شوند.

---

# ۸.۱۹. بررسی بدافزار

# ۸.۲۲. حذف امن فایل

اگر استاد مدرکی را حذف کرد، بلافاصله و کورکورانه Object حذف نمی‌شود.

ابتدا بررسی می‌شود فایل در بخش دیگری استفاده نشده باشد.

همچنین Soft Delete برای Metadata خواهیم داشت تا سابقه مهم مدیریتی و امنیتی حفظ شود.

# ۸.۲۳. ثبت رویدادهای مدیریتی

کارهای حساس ثبت می‌شوند، مانند:

- چه مدیری استاد را تأیید کرد؟
- چه کسی درخواست را رد کرد؟
- چه زمانی مدرکی تأیید شد؟
- چه کسی فایل خصوصی را مشاهده کرد؟
- چه کسی وضعیت تخصص را تغییر داد؟

این بخش بعداً به Audit Log مرکزی متصل خواهد شد.

# خروجی نهایی مرحله ۸

در پایان مرحله ۸ باید بتوانیم این سناریو را از ابتدا تا انتها اجرا کنیم:

**کاربر درخواست استادشدن می‌دهد → پروفایل حرفه‌ای خود را تکمیل می‌کند → تخصص‌ها و زبان‌ها را انتخاب می‌کند → مدارک خصوصی را آپلود می‌کند → سیستم فایل‌ها را اعتبارسنجی و اسکن می‌کند → پرونده برای مدیریت ارسال می‌شود → مدیر مدارک و تخصص‌ها را بررسی می‌کند → استاد تأیید می‌شود → استاد خدمات و تعرفه‌های خود را تعریف می‌کند → مدیریت در صورت نیاز آنها را تأیید می‌کند → پروفایل عمومی استاد با خدمات تأییدشده منتشر می‌شود.**

یعنی **مرحله ۸ را زمانی تمام‌شده حساب می‌کنیم که چرخه کامل «ثبت‌نام استاد تا انتشار پروفایل و خدمات استاد» واقعاً قابل اجرا باشد، نه صرفاً اینکه چند جدول و فرم ساخته شده باشند.**
