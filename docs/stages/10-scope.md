تغییراتی که گفتید بسیار مهم است و باعث می‌شود مرحله ۱۰ دیگر فقط «جستجوی استاد» نباشد، بلکه تبدیل شود به **هسته چندزبانه پلتفرم (Multilingual Knowledge & Discovery Engine)** که بعداً پایه ترجمه کل سایت، چت چندزبانه، هوش مصنوعی و ارتباط جهانی خواهد بود.

بنابراین مرحله ۱۰ را از نو با این معماری بازطراحی می‌کنیم.

# مرحله ۱۰ — موتور جستجو، تطبیق استاد و زیرساخت چندزبانه جهانی

## هدف اصلی مرحله

ساخت یک سیستم که بتواند:

1. کاربر با هر زبان از بین ۱۴۷ زبان سایت جستجو کند.
2. تمام محتوای سایت قابلیت ترجمه به همه زبان‌ها داشته باشد.
3. استادان، تخصص‌ها، خدمات و صفحات داشبورد چندزبانه باشند.
4. جستجو براساس مفهوم، نه فقط کلمه، انجام شود.
5. پایه آماده برای:
   - چت متنی چندزبانه با AI
   - مکالمه صوتی ترجمه‌شده
   - دستیار هوشمند انتخاب استاد
   - ترجمه زنده جلسات

باشد.

# ۱۰.۱. تصمیم معماری اصلی زبان

❌ استفاده از فایل ترجمه:

مثلاً:

```
fa.json
en.json
ar.json
```

برای این پروژه مناسب نیست.

چون:

- محتوا پویا است.
- استادان زیاد می‌شوند.
- صفحات داشبورد زیاد هستند.
- کاربران محتوا تولید می‌کنند.
- ترجمه باید قابل مدیریت باشد.

بنابراین:

✅ سیستم ترجمه Database Driven طراحی می‌شود.

# ۱۰.۳. جدول زبان‌ها

جدول:

```
languages
```

تمام زبان‌های مورد پشتیبانی.

ساختار:

| field                 | توضیح        |
| --------------------- | ------------ |
| id                    | شناسه        |
| code                  | کد ISO       |
| name_en               | نام انگلیسی  |
| native_name           | نام بومی     |
| direction             | LTR/RTL      |
| status                | فعال/غیرفعال |
| ai_supported          | پشتیبانی AI  |
| speech_supported      | تبدیل صوت    |
| translation_supported | ترجمه        |

نمونه:

```
1
en
English
LTR


2
fa
فارسی
RTL


3
ar
العربية
RTL
```

# ۱۰.۱۶. تعداد استادان و طراحی Scale

با فرض:

حداکثر:

```
3000 استاد
```

نیاز به معماری سنگین Enterprise نداریم.

اما باید آماده رشد باشد.

طراحی:

- PostgreSQL برای داده اصلی
- OpenSearch برای جستجو
- Redis برای Cache
- Queue برای Translation/Event

کاملاً کافی است.
