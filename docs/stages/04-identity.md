# مرحلهٔ ۴ — هویت ایمیلی و امنیت نشست

این مرحله ثبت‌نام و ورود ایمیل/رمز، تأیید ایمیل، بازیابی رمز، هش Argon2id، نشست قابل ابطال و محدودیت تلاش را پیاده می‌کند. OTP، Magic Link، OAuth و MFA برای مرحلهٔ ۵ هستند. مجوزهای نقش/سازمان و محافظت از منابع کسب‌وکار در مرحلهٔ ۶ پیاده می‌شوند؛ پیش‌نمایش داشبوردهای مرحلهٔ ۳ همچنان عمومی و با دادهٔ نمونه است.

## صفحه‌ها

همهٔ مسیرها نسخهٔ `/en` و `/fa` و پیشوند اختیاری build دارند:

- `/fa/auth/register`: ثبت‌نام و صف ایمیل تأیید؛
- `/fa/auth/login`: ورود پس از تأیید ایمیل؛
- `/fa/auth/resend-verification`: درخواست دوبارهٔ لینک؛
- `/fa/auth/verify-email`: مصرف لینک با کلیک کاربر؛
- `/fa/auth/forgot-password` و `/fa/auth/reset-password`: بازیابی؛
- `/fa/account/security`: دادهٔ واقعی حساب و نشست‌های خود کاربر، ابطال یک نشست/همه و خروج.

فرم‌ها با وزیر محلی، Font Awesome، فارسی RTL و انگلیسی LTR ساخته شده‌اند. صفحهٔ امنیت فقط دادهٔ API احرازشده را می‌گیرد؛ دادهٔ نمونه به جای حساب واقعی نمایش داده نمی‌شود. اگر تنظیمات هویت حاضر نباشد، فرم پیام روشن «هنوز تنظیم نشده» می‌دهد.

## مرز سرویس و قرارداد HTTP

مرورگر فقط با `/api/auth/:action` در Next.js روی همان مبدأ صحبت می‌کند. BFF درخواست‌های نوشتن را با Origin دقیق و JSON کنترل می‌کند، ورودی را به ۸ کیلوبایت محدود و توکن‌ها را از پاسخ عمومی حذف می‌کند. سپس درخواست به Gateway و از آنجا به Identity می‌رود. Gateway و Identity هر دو کلید داخلی را بررسی می‌کنند؛ header هویت/نقش/tenant از مرورگر قابل اعتماد نیست.

API داخلی `/api/v1/auth`:

| روش  | action                                | ورودی                                            |
| ---- | ------------------------------------- | ------------------------------------------------ |
| POST | register                              | email, password, locale                          |
| POST | login                                 | email, password                                  |
| POST | forgot-password / resend-verification | email, locale                                    |
| POST | verify-email                          | token                                            |
| POST | reset-password                        | token, password                                  |
| POST | refresh / logout                      | refresh؛ فقط BFF از کوکی می‌خواند                |
| GET  | session                               | توکن access داخلی از کوکی BFF                    |
| POST | revoke                                | id اختیاری؛ نبود id یعنی همهٔ نشست‌های خود کاربر |

فیلد اضافی مثل role یا tenant رد می‌شود. همهٔ پاسخ‌ها `no-store` هستند. ایمیل normalize و با unique index ذخیره می‌شود. رمز ۱۵ تا ۱۲۸ نویسه است؛ ترکیب مصنوعی کاراکترها تحمیل نمی‌شود. Argon2id با memory=19456KiB، time=2 و parallelism=1، salt تصادفی مستقل دارد.

توکن‌های opaque با ۳۲ بایت تصادفی ساخته می‌شوند و فقط SHA-256 آن‌ها در جدول نشست/لینک نگه داشته می‌شود. access پنج دقیقه اعتبار دارد؛ refresh با هر مصرف عوض می‌شود، مهلت بیکاری هفت روز و سقف مطلق سی روز است. تاریخچهٔ refresh تا پایان عمر خانواده باقی می‌ماند. مصرف دوبارهٔ refresh قبلی، کل همان نشست را با تراکنش قطعی باطل می‌کند؛ دو درخواست هم‌زمان عمداً هر دو موفق نمی‌شوند. چند تب باید از تمدید هم‌زمان پرهیز کنند؛ مصرف توکن قدیمی ورود دوباره می‌خواهد.

کوکی production نام `__Secure-vianoor-*`، HttpOnly، Secure، SameSite=Lax و Path برابر زیرمسیر نصب دارد. توکن در localStorage یا JSON مرورگر قرار نمی‌گیرد. فقط localhost آزمایشی می‌تواند HTTP و کوکی بدون Secure داشته باشد.

بازیابی رمز تمام نشست‌های حساب را باطل می‌کند و ورود خودکار انجام نمی‌دهد. لینک تأیید ۲۴ ساعت و لینک بازیابی ۳۰ دقیقه معتبر است. لینک‌ها یک‌بارمصرف‌اند؛ ارسال دوباره، لینک قبلی همان هدف را باطل می‌کند. secret در fragment لینک است تا در درخواست GET و referrer ارسال نشود؛ صفحهٔ لینک referrer policy برابر no-referrer دارد و GET لینک را مصرف نمی‌کند.

## ایمیل، رویداد و ممیزی

ثبت حساب، token hash و job ایمیل در تراکنش دیتابیس Identity ثبت می‌شوند. نشانی مقصد و متن شامل لینک در صف اختصاصی با AES-256-GCM و `AUTH_MAIL_KEY` رمز می‌شوند. worker با قفل SKIP LOCKED و SMTP ارسال می‌کند؛ شکست بدون log کردن پیام/خطای provider تکرار می‌شود. پیام موفق یا منقضی از صف حذف می‌شود. تحویل حداقل یک‌بار است؛ crash پس از SMTP می‌تواند همان ایمیل را دوباره بفرستد، اما لینک همچنان یک‌بارمصرف است.

رویداد `identity.account.registered.v1` از outbox مرحلهٔ ۲ منتشر می‌شود و تنها شناسهٔ حساب را دارد. audit محلی Identity رویدادهای امنیتی و شناسه را نگه می‌دارد؛ اتصال مصرف‌کنندهٔ Audit/Notification مربوط به مراحل بعد است. queue و جدول‌های Identity وارد دیتابیس سرویس دیگری نمی‌شوند.

SMTP در محیط اصلی TLS الزامی دارد. موفقیت درخواست ثبت‌نام به معنی قرارگرفتن در صف است، نه اثبات رسیدن ایمیل به Inbox کاربر. `/health/ready` سلامت DB/Redis/NATS را می‌سنجد؛ سلامت تحویل ایمیل باید با صف و provider بررسی شود. اگر SMTP یا دامنه/اعتبارنامه هنوز تنظیم نشده باشد، نباید ادعای ارسال واقعی کرد.

## محدودیت تلاش

محدودکننده Redis اتمیک است: ورود هر ایمیل ۸ بار در ۱۵ دقیقه؛ register/forgot/resend هرکدام ۴ بار برای هر ایمیل در ۱۵ دقیقه؛ ورودی هر client حداکثر ۱۲۰ درخواست در دقیقه؛ refresh هر توکن ۳۰ بار در دقیقه. کلیدها hash می‌شوند و ایمیل/IP خام در Redis key نیست. حداکثر چهار درخواست هم‌زمان در هر process Identity پذیرفته می‌شود. خرابی Redis دسترسی را باز نمی‌کند.

BFF به‌طور پیش‌فرض از bucket مشترک ورودی استفاده می‌کند. فقط وقتی reverse proxy **هدر x-real-ip را بازنویسی می‌کند**، `AUTH_TRUST_PROXY=1` را برای تفکیک client فعال کنید. صرفاً عبور دادن هدر کاربر قابل اعتماد نیست. این تنظیم جای محدودیت اتصال و DDoS در ورودی شبکه را نمی‌گیرد.

پاسخ ثبت‌نام تکراری و درخواست بازیابی حساب ناموجود عمومی و هم‌شکل است. درخواست‌های ایمیلی حداقل زمان پاسخ مشابه دارند و SMTP از مسیر پاسخ جداست؛ این آزمون تضمین ریاضی رفع تمام کانال‌های زمانی نیست.

## نصب مستقل آزمایشی

Docker Compose 2.30+ لازم است؛ env_file با format=raw از تفسیر کاراکترهای رمز SMTP جلوگیری می‌کند. یک checkout تازه استفاده کنید. هیچ credential/volume مرحلهٔ ۲ را بازسازی یا بازنویسی نکنید.

```bash
node scripts/infra/prepare.mjs
AUTH_DEVELOPMENT=1 node scripts/identity/prepare.mjs
VIANOOR_AUTH_WEB_PORT=15400 docker compose -f infra/identity.compose.json up -d --build --wait
```

سپس `http://127.0.0.1:15400/vianoor/fa/auth/register`. Mailpit فقط داخل شبکهٔ Docker آزمایش فعال است و SMTP واقعی بیرونی نیست. آزمون کامل:

```bash
docker compose -f infra/identity.compose.json run --rm identity-test
```

در نصب اصلی، ابتدا متغیرهای `AUTH_PUBLIC_URL` (HTTPS و شامل زیرمسیر)، `SMTP_HOST`، `SMTP_PORT`، `SMTP_FROM`، و در صورت نیاز `SMTP_USER` و `SMTP_PASSWORD` را در محیط امن تنظیم کنید؛ `AUTH_DEVELOPMENT` را فعال نکنید. سپس prepare را اجرا کنید. کلیدهای تصادفی در `infra/local` ساخته می‌شوند. این پوشه و `identity.compose.json` از Git کنار گذاشته شده‌اند. کلید رمز صف را همراه backup دیتابیس نگه دارید و بدون برنامهٔ چرخش عوض نکنید.

پورت‌های پیش‌فرض نصب جدید وب 18874 و Gateway 18873، فقط روی loopback هستند؛ این نصب خودکار وب قدیمی یا Nginx را جابه‌جا نمی‌کند. نام پروژهٔ Compose مستقل `vianoor-stage4` است. مسیر stage2 و volumeهای آن دست‌نخورده باقی می‌مانند. تغییر پورت وب در محیط آزمایشی باید با AUTH_PUBLIC_URL هم‌خوان باشد.

تنظیم SSH، دامنهٔ شخصی، کلید واقعی و فایل Nginx در Git قرار نمی‌گیرند. اتصال SMTP واقعی، DNS ارسال و تست روی VPS کاربر هنوز نیازمند اجرا در همان محیط است.

## شواهد و محدودیت‌ها

آزمون‌ها در [گزارش مرحلهٔ ۴](../testing/stage-04.md) آمده‌اند. پاک‌سازی دوره‌ای حساب‌های تأییدنشده و retention audit باید قبل از عرضهٔ عمومی با سیاست نگهداری داده تکمیل شود. این مرحله ادعای تکمیل MFA، RBAC، پنل عملیاتی نقش‌ها یا ممیزی امنیتی مستقل ندارد.
